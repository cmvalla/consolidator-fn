# Consolidator Cloud Function

The `consolidator` Cloud Function is a core component of the graph processing pipeline. Its primary responsibility is to aggregate partial graph data, perform advanced graph analysis (clustering, deduplication, community detection), and prepare the consolidated graph for persistence in Cloud Spanner.

## Purpose

The main purpose of the `consolidator` function is to transform fragmented graph data, typically generated by worker functions, into a coherent and enriched knowledge graph. This involves several key steps that enhance the quality and utility of the graph data before it is stored in the central Spanner database.

## Input

The `consolidator` function is triggered by a Pub/Sub message. The message payload contains the following information:

*   **`batch_id` (string)**: A unique identifier for the current batch of graph data being processed. This ID is used for locking mechanisms in Spanner to ensure atomicity and prevent race conditions during concurrent processing.
*   **`gcs_paths` (list of strings)**: A list of Google Cloud Storage (GCS) URIs. Each URI points to a serialized `igraph` object (typically a Python `pickle` file) representing a partial graph generated by a worker function.

## Processing Steps

Upon receiving a Pub/Sub message, the `consolidator` performs the following sequence of operations:

1.  **Acquire Lock**:
    *   Attempts to acquire a distributed lock in the Cloud Spanner `WorkflowStatus` table using the provided `batch_id`. This prevents multiple `consolidator` instances from processing the same batch concurrently.
    *   If the lock cannot be acquired (e.g., another instance is already processing, or the batch is already completed), the function exits.

2.  **Download Partial Graphs**:
    *   Iterates through the `gcs_paths` provided in the Pub/Sub message.
    *   For each GCS URI, it downloads the corresponding serialized `igraph` object from the specified GCS bucket.
    *   The downloaded `igraph` objects represent partial graphs.

3.  **Merge Graphs**:
    *   Merges all downloaded partial `igraph` objects into a single, comprehensive `igraph` object. The merging is performed `byname=True`, meaning vertices and edges with the same `name` attribute are treated as the same entity/relationship across different partial graphs.

4.  **Clustering and Entity Merging (`cluster_and_merge_entities`)**:
    *   Identifies similar entities within the merged graph based on their embeddings (if available) and a defined similarity threshold.
    *   Creates new "Class" entities to represent clusters of similar "Instance" entities.
    *   Establishes `INSTANCE_OF` relationships between the original "Instance" entities and their newly created "Class" entities.
    *   Propagates relationships from instances to their corresponding classes, creating higher-level relationships between classes.

5.  **Entity Deduplication (`deduplicate_entities`)**:
    *   Resolves duplicate Entity IDs (EIDs) that might still exist after initial merging and clustering.
    *   Handles duplicate "Class" entities by merging them (e.g., selecting the class with the most instances as the canonical one).
    *   Renames duplicate "Instance" entities by appending a unique suffix to their EIDs to ensure all entities have unique identifiers.

6.  **Community Detection (`run_igraph_community_detection`)**:
    *   Applies community detection algorithms (specifically, maximal cliques using `igraph`) to identify densely connected groups of entities within the graph.
    *   Creates new "Community" entities for each detected community.
    *   Associates original entities with the "Community" entities they belong to.
    *   Generates summaries and embeddings for the newly created "Community" entities using LLM operations.

7.  **Remove Entities with Null Keys (`remove_entities_with_null_keys_and_relationships`)**:
    *   Performs a final data cleaning step by removing any entities that have null or empty IDs, along with their associated relationships, to maintain graph integrity.

8.  **Serialize and Upload Final Graph**:
    *   Serializes the final, processed `igraph` object (which now includes clustered entities, deduplicated entities, and community information) into a Python `pickle` file.
    *   Uploads the serialized graph to a designated GCS bucket (`GRAPH_DATA_BUCKET_NAME`). The object name includes the `batch_id` and a timestamp for traceability.

9.  **Publish Pub/Sub Message to Persistor**:
    *   Publishes a new Pub/Sub message to the `persistor` function's topic (`PERSISTOR_TOPIC_NAME`).
    *   The message payload includes the `batch_id` and the GCS URI of the newly uploaded consolidated graph. This signals the `persistor` function to retrieve and store the data in Cloud Spanner.

10. **Release Lock**:
    *   Releases the lock in the Cloud Spanner `WorkflowStatus` table, updating the batch status to "PENDING_PERSISTENCE" (or "FAILED" if an error occurred).

## Output

The primary output of the `consolidator` function is a serialized `igraph` object stored in a GCS bucket, along with a Pub/Sub message notifying the `persistor` function of the new data. The function also updates the `WorkflowStatus` table in Cloud Spanner to reflect the processing status of each batch.

## Error Handling

The function includes error handling mechanisms to log exceptions and release the Spanner lock with a "FAILED" status if any critical errors occur during processing. This ensures that the system can recover and potentially retry failed batches.
